# ADR-0003. Удалённый доступ к панели: API клиента, операторы, Telegram (Фаза 8)

Статус: принято владельцем 2026-10-15 (Telegram допустим, бот пользователя; доступ включает сам пользователь; операторы = администраторы, число задаёт пользователь). Шаг 1 (SSH, мост MCP по принудительной команде) уже сделан; здесь — шаги 2–3.

## Две роли
- **Агент** — ИИ-клиент: инструменты шлюза по уровням (как по сокету), токен агента. Предлагает планы, не одобряет.
- **Оператор** — человек-администратор: смотрит состояние и аудит, одобряет/отклоняет планы L2 удалённо. Токен оператора **не принимается** на `/agent/v1`, токен агента — на `/operator/v1` (разные реестры).

## Решения
1. **Отдельный слушатель** (`remote_api.py`), **выключен по умолчанию**. API панели на `127.0.0.1:8765` и сокет агентов не меняются и наружу не выставляются.
2. **Адрес задаёт пользователь**: `127.0.0.1` (за туннелем/обратным прокси), адрес LAN/VPN или `0.0.0.0`. Не-loopback адрес **требует TLS** и непустой **список разрешённых адресов** (CIDR); иначе слушатель не стартует (fail closed). TLS: самоподписанный сертификат создаёт `openssl` (RSA-2048), отпечаток показывается в панели для закрепления клиентом.
3. **Токены**: 256 бит случайности, токены оператора с префиксом `sao_` (токены агентов — прежнего формата), в реестре только SHA-256, сравнение за постоянное время, показываются **один раз**; отзыв и ротация; срок жизни по желанию. Ограничение попыток: 10 неудач с адреса за минуту → блок на 5 минут; общий лимит запросов на токен.
4. **Права оператора**: `read` (статус, планы, аудит) и/или `approve`. Удалённое одобрение — ещё и **глобальная настройка** (по умолчанию выкл., запись в аудит, ослабляет защиту как «кнопка в панели»). Одобрение требует: токен с `approve`, **TOTP-код** оператора (RFC 6238, секрет показывается один раз; код одноразовый), **эхо хеша** плана (`digest`) и план уровня L2. **L3 удалённо одобрить нельзя никогда** — только системный диалог на машине с панелью. Решение пишется `by=operator:<имя>`.
5. **Агент не может одобрить**: его токен не даёт доступа к `/operator/v1`; одобрение требует токена и TOTP оператора, которых у агента нет.
6. **Telegram**: бот **сам опрашивает** Telegram (исходящий HTTPS, входящий порт не нужен); принимаются только личные чаты с `chat_id`, привязанным к оператору; одобрение — команда с TOTP-кодом (украденный аккаунт Telegram без кода не одобрит); токен бота — файл 0600; в сообщения идут краткое описание плана и id, без секретов. Уведомления о новых планах — операторам с правом `approve`.
7. **Что оператору нельзя** (в этой версии): запускать операции, менять настройки, управлять агентами и операторами — только чтение и одобрение/отклонение планов. Это наименьшие права под задачу «контролировать».
8. **Аудит**: каждый удалённый запрос (адрес, кто, путь, код ответа); неудачная аутентификация — с ограничением частоты записей.
9. **Жёсткие рамки**: тело ≤ 64 КБ, только JSON, таймаут соединения 15 с, ограниченное число одновременных соединений, без CORS.

## Угрозы и ответ
| Угроза | Ответ |
|---|---|
| Подбор/кража токена агента | токены 256 бит, хеши, лимит попыток, allow-list, TLS; агент ограничен своим уровнем |
| Агент одобряет свой план | другой реестр и область; нужен TOTP; L3 только диалог; локальный агент с оболочкой — известный остаточный риск (ADR-0001) |
| Кража токена оператора | без TOTP одобрить нельзя; чтение — по `read`; отзыв |
| Кража аккаунта Telegram | одобрение требует TOTP; ограничение по `chat_id` |
| Повтор перехваченного запроса | TOTP одноразовый; `digest` привязывает к плану; TTL плана 15 мин |
| MITM в LAN | TLS обязателен вне loopback; закрепление отпечатка |
| DoS | лимиты тела, соединений, попыток, запросов на токен |
| Подмена плана между показом и одобрением | эхо `digest` проверяется на сервере |
| Утечка секретов в аудит/Telegram | маскирование аудита; сообщения без параметров-секретов |

## Изменения по итогам независимого ревью (2026-10-15)
- **Блокировка TOTP**: 5 неверных кодов подряд → оператор блокируется для одобрения (API и Telegram); снимает только человек в панели («Разблокировать»); записи об ошибках в аудите ограничены по частоте.
- **Любая ротация оператора и любое изменение прав/чата у оператора, который имеет или получит право `approve`, — через диалог**, текст диалога называет действие; выдача `approve` выдаёт НОВЫЕ токен и секрет TOTP (показываются один раз). Имена операторов — только ASCII.
- **Слушатель**: проверка адреса и лимит соединений ДО разбора запроса; TLS-рукопожатие в рабочем потоке с таймаутом (молчащее TCP-соединение больше не замораживает приём); общий срок на запрос 30 с (slowloris); loopback-адреса не блокируются (за обратным прокси все клиенты — 127.0.0.1), защита там — энтропия токена и блокировка TOTP; списки адресов шире /8 (IPv4) и /32 (IPv6) запрещены; диалог при открытии наружу всегда показывает итоговый список адресов.
- **Telegram**: у каждого запуска бота своё событие остановки, выключенный бот не обрабатывает сообщения и завершает потоки; в уведомлениях и `/plans` видны параметры плана; настройки пишутся атомарно с перечитыванием после диалога.
- **Повторное ревью исправлений** нашло ещё: повышение уровня агента и «не спрашивать» (`/api/agent-gateway/settings`) и выдача токена агента (любого уровня) теперь только через системное окно (раньше локальный HTTP-клиент мог создать самоодобряющего L2-агента без окон); любая привязка Telegram-чата и разблокировка оператора — через окно, состояние оператора, показанное в окне, проверяется при записи; TLS-соединения закрываются после ответа (была утечка дескрипторов), срок 30 с — только на приём запроса, а не на работу инструмента; `verify_request` не может уронить слушатель; повторно присланный верный код TOTP не считается подбором, заблокированный оператор получает отдельный ответ; смещение Telegram хранится на диске; `plans.approve/_decide/reject` под одной блокировкой.
- Прочее: `plans.approve` под блокировкой; выдача токена агента L3 — через диалог; `shlex.quote` в принудительной команде SSH; `limit` в аудите не вызывает 500.

## Остаточные риски
- **Агент того же пользователя ОС с оболочкой может писать в `~/.service-admin`** (`remote.json`, `operators.json`, `plans.json`, токен бота) и обойти диалоги: как и до Фазы 8, он может сам выставить статус плана «одобрен». Диалоги защищают от агента, ограниченного HTTP-API/чтением файлов; от агента с оболочкой — изоляция (отдельный пользователь или ВМ), см. ADR-0001.
- За обратным прокси список адресов не действует (все клиенты — 127.0.0.1): ограничивайте доступ на прокси.
- Telegram: TOTP-код не привязан к плану; сервер Telegram, видя `/approve <id> <хеш> <код>`, мог бы подменить команду на другой ожидающий план в пределах окна кода. Присущий каналу риск.
- Для Telegram токен оператора не нужен: достаточно привязки чата и кода TOTP; локальный агент, читающий `operators.json`, получает секрет TOTP (но привязка чата требует диалога).
- Сертификат самоподписанный: клиент должен закрепить отпечаток; обратный прокси с настоящим сертификатом предпочтительнее для интернета.
- Секрет TOTP и хеши лежат в `~/.service-admin/operators.json` (0600): локальный агент того же пользователя может их прочитать (но не токен оператора).
- Telegram — сторонний сервер: он видит краткие описания планов и факт одобрения.
