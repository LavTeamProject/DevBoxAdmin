# План работ (Roadmap)

Этот документ — **единственное место**, где описан план работ по проекту. Если работы нет в этом
файле — она не согласована. И если пункт здесь есть, но порядок фаз нарушен — это тоже ошибка.

Обозначения: ⛔ снято · ✅ готово · 🔶 написано, проверено частично · 🔜 следующее · ⬜ не начато · 🚫 вне рамок (сознательно не делаем)

---

## Принципы, обязательные для всех фаз

1. **Без зависимостей.** Backend — чистый Python stdlib, frontend — vanilla JS/CSS, без сборки, без CDN.
2. **Только `127.0.0.1`.** Панель никогда не слушает сеть. Доступ с MacBook — через SSH-туннель:
   `ssh -L 8765:127.0.0.1:8765 mac-mini`.
3. **Пути только из реестра сервера.** Браузер никогда не может запросить произвольный путь.
4. **Действия, меняющие систему, обязаны иметь `data-confirm`** и идти через `start_job` /
   `start_steps`, а не выполняться внутри обработчика запроса.
5. **Панель обязана уметь поставить себя на чистую macOS.** Это цель продукта, а не пожелание:
   одна панель, которая настраивает и контролирует всю машину. Всё, что мешает этому, — дефект.
6. **Каждая фаза полезна и проверяема сама по себе** — никаких фаз, которые лишь «готовят» другую.
7. **Никаких костылей.** Делаем сразу в правильной форме; временные мосты запрещены, даже если
   они ускоряют текущий шаг.

## Фаза 2 — Панель становится самодостаточной (🔜 следующее)

Порядок внутри фазы **обязателен**: 2.0 → 2.1 → 2.2, и только после них 2.3+.

### 2.0 Bootstrap: запуск на чистой macOS (✅ проверено в ВМ, кроме отмеченного)

Проблема, которую это решает (проверено на фактах):

- в чистой macOS **Python нет вообще** (`/System/Library/Frameworks/Python.framework` отсутствует);
- Command Line Tools дают только `/usr/bin/python3` = **3.9.6**, а код требует 3.11 из-за `tomllib`;
- значит **панель не может себя запустить** — «дружественный интерфейс» негде показать.

Решение — **вшить собственный интерпретатор**, а не занимать системный:

- ✅ `install.sh` скачивает автономный CPython из `python-build-standalone` в
  `~/.service-admin/runtime/python/` (`fetch-python.sh`: поиск релиза, проверка SHA256, атомарная
  установка, идемпотентность). **Проверено на чистой macOS 26.6 в ВМ (tart):** Python 3.12.15,
  панель работает на нём (`/api/runtime` → `bundled: true`), повторный запуск ничего не качает.
  **Не проверено:** сценарий неверной контрольной суммы.
- ✅ Launcher собирается через `/usr/bin/osacompile` (`macapp/launcher.applescript`, иконка
  `macapp/AppIcon.icns` лежит в репозитории) вместо `swiftc`. **Проверено:** сборка, подпись,
  запуск сервера и завершение за 2 с. **В ВМ на чистой macOS проверены оба пути:** через LaunchAgent
  и запасной (агент остановлен → приложение само поднимает сервер вшитым Python).
  **Не проверено:** диалог «сервер не отвечает»; визуально — что страница открылась в браузере гостя.
- ✅ На чистой macOS допустимо предполагать только: `curl`, `tar`, `osacompile`, `open`, `osascript`
  (+ `shasum`, `grep`, `sed`, `uname`, `PlistBuddy`, `codesign`, `defaults`, `sips`/`iconutil`).
  **Подтверждено в ВМ:** все эти утилиты есть на чистой macOS 26.6.
- ✅ `install.sh` доводит до конца без единого предварительного условия: скачал → распаковал →
  собрал приложение → запустил LaunchAgent (~10 с). **Подтверждено в ВМ.** Проверка нашла и
  исправила баг: `git rev-parse` в `install.sh` вызывал на чистой системе заглушку Apple,
  которая открывала диалог установки CLT посреди установки; теперь `git` зовётся только при
  наличии CLT. Открытие браузера (без `--no-open`) в ВМ визуально не проверено.
  ⚠️ То же касается любого вызова `git`/`python3` из панели на чистой системе — учесть в 2.1.
- ✅ Проверка версии: `/api/runtime` + заметка в сайдбаре «Запущено не вшитым Python» (RU/EN).
  **Проверено:** в браузере на системном интерпретаторе (заметка видна) и в ВМ на вшитом
  (`bundled: true`).
- ✅ `tomllib` получает запасной путь (`tomllib` → `tomli` → валидация TOML отключается с честным
  сообщением). Проверено на Python 3.12 и 3.9.6 (с `tomli` и без). **Разрешение владельца проекта
  получено** — см. `CLAUDE.md`, «Keputusan arsitektur». Это защита, а не основной путь.

- ✅ **Защита от заглушек CLT** (найдено в ВМ): `/usr/bin/git`, `python3`, `make`, `xcrun` и др. без CLT —

- 🔶 «Остальной интерфейс не притворяется рабочим»: сделан баннер «Не хватает: …» на всех страницах и

  Нужно: у каждой страницы своё понятное «чего не хватает» + кнопка «поставить».
- ✅ Действия мастера пишутся в журнал аудита (см. 2.2): запрос, `job_id`, завершение задачи с кодом.

**Факты чистой macOS, найденные при проверке (учитывать в UX):**

- При первом запуске **macOS показывает запросы доступа** к «Документам» и «Рабочему столу» для Python

- Диалог CLT может отказать по месту на диске (см. выше), а панель об этом не узнаёт — только ждёт.

## Фаза 4 — Agent Control API: управление машиной для ИИ-агентов (🔶 4.0–4.5 сделаны; не проверены клиенты Codex/OpenCode/Gemini)

**Принцип:** не интегрироваться с каждым агентом по отдельности (Claude Code, Codex, OpenCode, Gemini,
свой агент). Панель становится **платформой операций**, а агенту выдаётся ограниченный доступ к ним.
Смена модели или поставщика не должна требовать переписывать механизм развёртывания.

**Зависимости (фаза не начинается раньше):** 2.2 журнал аудита, 2.3 снимки, 2.4 профили установки
выполняются, фоновые jobs. Агент без аудита и идемпотентных операций — это неуправляемый риск.
Срез на чтение (4.0) зависит только от 2.2.

**Область (решение владельца принято):** агент живёт **на Mac клиента** (например, установленный
там Claude Code) и подключается к панели локально. Локальный MCP — достаточная архитектура; облачный
аккаунт и внешняя авторизация не нужны. Удалённое управление парком машин — в «Вне рамок» ниже.

**Что эта фаза гарантирует — и чего нет (честно).** Агент на том же Mac обычно имеет собственный
Bash и может обойти любой API обычными командами. Поэтому:

- Реальная граница безопасности — **очередь подтверждений в панели, которую одобряет человек**.
  Credential агента её не создаёт: он лежит в конфиге MCP, а этот конфиг агент может прочитать.
- Ценность API — **аудит, идемпотентность, проверка результата, единый контракт**, а не изоляция.
  Не описывать и не продавать это как «агент заперт».
- Настоящая изоляция (недоверенный код, раннеры) возможна только в ВМ — это Фаза 5.

Не путать с 2.7: там панель *запускает* агентов в PTY для работы с кодом. Здесь агент *управляет
самой машиной* через панель. Роли разделены, права на них настраиваются отдельно:
**агент-разработчик** (код в репозитории, разрешённые команды проекта) и **агент-администратор**
(ПО, контейнеры).

### 4.5 Цикл «диагностика → исправление» (🔶 границы и эскалация сделаны)

Диагностика → план → согласование → исполнение (jobs) → проверка (health checks/тесты/сборка,
сравнение со снимком из 2.3) → исправление.

- ✅ Жёсткие границы (сервер, `plans._escalation`): за час 2 неудачи/отклонения ОДИНАКОВОГО плана или 4 неудачи агента
  подряд → `plan.escalate` («стоп, сообщите пользователю»), событие `plan:escalate` в аудите. Плюс уже действующие:
  5 открытых планов, 10 исполнений/час, один раз на план, `plan.stale`. Проверено на синтетических планах (4 случая); живой агент — нет.
- ✅ **Лимит времени цикла** (`plans`): задача плана (кроме L3) живёт не дольше 30 мин — её останавливает сервер (`plan:timeout` в аудите, статус `failed`, `error=timeout`); суммарное время задач агента за час ≤ 45 мин, иначе `plan.cycle_budget` («остановитесь и сообщите пользователю»). Время окончания фиксирует `_watch`.
- ✅ **Сравнение со снимком после исправления:** для `package.install` и `profile.install` перед исполнением автоматически делается снимок «до» (`snapshot_before`, подпись `plan <id> before`; нет места/сбой — идём без него, событие `plan:snapshot_skipped`), а `verify_plan` возвращает `snapshot_diff` (что добавилось/убралось/изменилось). Проверено на подменах (таймаут, бюджет, diff); с живым агентом и реальным brew — нет. Ограничение: снимки накапливаются (предел 200) — старые удаляет человек.

## Фаза 8 — Удалённое управление панелью (✅ шаг 1 SSH сделан; ⬜ API-клиент и Telegram — по решению владельца)

Запрос владельца: панель крутится на сервере, а управлять ею можно **с другой машины**: по SSH, из Telegram, и через **API-клиент** (чтобы можно было сделать своё приложение/чат-бота). Сейчас панель слушает только `127.0.0.1`, агенты — только через локальный Unix-сокет (раздел «Вне рамок»: вынос в сеть — отдельное решение). Эта фаза и есть такое решение; до утверждения не реализуется.

**Две роли, их нельзя смешивать.**
- **Агент** (ИИ-клиент): инструменты шлюза по уровням L1–L3; изменения — только планом, который одобряет **человек**.
- **Оператор** (человек в приложении/боте): смотрит состояние и аудит, **одобряет или отклоняет планы**, останавливает задачи. Это сильнее агента, поэтому защита строже; одобрение оператора не должно совпадать с каналом агента (агент не может одобрить свой план ни одним способом).

**Каналы (по возрастанию риска и работы):**
1. **SSH (≈ 2–3 дня).** Панель остаётся на localhost; `ssh -L` пробрасывает сокет/порт; готовая команда и конфиг MCP на странице «Подключение агентов», `service-admin` CLI по ssh. Почти нового кода нет; проверка на двух ВМ (панель отдельно, агент отдельно).
2. **API клиента (≈ 1–2 недели).** Версионированный `/agent/v1` и `/operator/v1`: токен на клиента с областями (scopes), TLS обязателен (или только за туннелем/обратным прокси), список разрешённых адресов, лимиты, отзыв, аудит с `by=remote:<клиент>`, выключатель в настройках (по умолчанию выкл.). Описание в OpenAPI; пример приложения/SDK.
3. **Telegram-бот (≈ 1 неделя после п. 2).** Бот сам **опрашивает Telegram исходящим соединением** (входящий порт не нужен); разрешён только список `chat_id` владельца; одобрение плана — кнопка в чате **плюс** одноразовый код, показанный на панели/в её окне (чтобы украденный аккаунт Telegram не одобрял сам); токен бота — в файле 0600. Сообщения проходят через серверы Telegram — в них нет секретов, только краткое описание плана.

**Что обязательно до реализации:** модель угроз и независимое ревью безопасности; тесты слоя A для удалённых вызовов; прогон слоя B с агентом на другой машине; запись в `docs/unverified.md`. Диалоги на экране сервера остаются каналом по умолчанию; удалённое одобрение — явная настройка, ослабляющая защиту, как «кнопка в панели».

**Решения владельца (2026-10-15):** Telegram допустим как канал — пользователь указывает **своего** бота; включать доступ из интернета, домашней сети или VPN должен **сам пользователь**, а панель сама предлагает типы подключения (блок «Удалённое подключение» на странице «Подключение агентов»); начинаем с SSH.

**Шаг 1 (SSH) — сделано, схема изменена по результатам проверки на ВМ.** Туннель `ssh -L` оказался небезопасным: ключ с `restrict,port-forwarding` всё равно выполняет команды на сервере и пробрасывает порт HTTP-API панели (полный API владельца). Принято: **принудительная команда** в `authorized_keys` — `command="<python> mcp_server.py --agent <id>",restrict <ключ>`. Ключ умеет только запустить мост MCP одного агента: нет оболочки, нет пробросов (TCP и Unix-сокет), произвольная команда игнорируется, секрет агента не покидает сервер (его не надо копировать). Клиент подключается так: `claude mcp add service-admin -- ssh -i <ключ> -o IdentitiesOnly=yes -o BatchMode=yes user@host`. Панель строит строку `authorized_keys` из вставленного публичного ключа (строго проверяет формат), сама файл не меняет. Проверено на двух машинах: сервер с панелью (ВМ) и клиент (Mac): 10 инструментов L1, `plan_changes` отклонён, `touch /tmp/PWNED` не выполнен, TCP/Unix-проброс не работает, нет pty. Тесты: `tests/test_remote_ssh.py`.

**Вопросы владельцу (остались):** (2) один оператор или несколько у одной панели (роль «оператор» = человек, одобряющий планы из приложения/бота)? (5) следующим шагом API-клиент или Telegram?

## 🚫 Вне рамок (сознательно)

- **Выносить панель в сеть.** Только SSH-туннель. Если когда-нибудь bind расширят — это отдельное
  решение, требующее аутентификации и разбора безопасности.
- **Удалённое управление машинами клиентов (control plane).** Сервер, клиентский коннектор с
  исходящим TLS-соединением, привязка машины одноразовым кодом, ключ в Keychain, изоляция
  арендаторов. Это отдельная архитектура и отдельная модель безопасности. Решено: агент живёт на
  Mac клиента (Фаза 4), поэтому облачный агент, управляющий Mac удалённо, не проектируется. Если
  понадобится — это новое решение владельца, а не продолжение Фазы 4.
- **Универсальный `execute_shell` для агентов и запуск агентов с правами root.**
- **Свой CI/CD внутри панели.** Уже есть Xcode Cloud / GitHub Actions; панель запускает и читает.
- **Выполнение произвольных shell-команд из формы.** Shell есть только во вкладке «Терминал».
