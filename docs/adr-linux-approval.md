# ADR-0001: Канал подтверждения действий агентов на Linux

Статус: **принято (проект), реализация — этап Л2**. Требует независимого ревью безопасности до выпуска.

## Контекст
На macOS человек одобряет план агента **системным диалогом** (`osascript`, кнопка по умолчанию «Отклонить», 110 с = отказ). Агент с терминалом на той же машине может обойти шлюз панели, но **не может нажать кнопку в диалоге**. На Linux диалога может не быть (сервер без экрана), а Python stdlib не умеет асимметричную криптографию.

**Модель угроз:** агент работает под тем же пользователем, что и панель, имеет shell (может читать файлы пользователя, запускать процессы, подключаться к HTTP-API панели, создавать PTY). Агент **не знает** пароль администратора и не имеет passwordless-sudo. Если passwordless-sudo у пользователя есть — защита по определению недостижима (root = всё): канал 2 в этом случае **отключается** (fail closed), а установщик предупреждает.

## Варианты
- **A. Диалог в графической сессии** (`zenity`/`kdialog`). Аналог macOS. Нужен экран и сессия пользователя. Агент не может нажать кнопку, но (X11) теоретически может синтезировать ввод в окно своего же пользователя — в Wayland это закрыто, в X11 нет → на X11 диалог **только** в режиме «ввод через xdotool/XTEST заблокирован» не гарантируем; документируем остаточный риск.
- **B. Одобрение через повышение привилегий** (`pkexec` + polkit-действие `auth_admin`, запасной вариант — `sudo` с `timestamp_timeout=0`). Работает по ssh без экрана, требует **пароль человека** при каждом одобрении. Решение пишет **root-владелец** (директория `/var/lib/service-admin/approvals/`, `root:root`); панель принимает только файлы с `st_uid == 0`. Крипто не нужно: подделать root-файл без root нельзя.
- **C. TOTP/код с телефона.** Секрет должен лежать где-то, откуда его не прочитает агент того же пользователя → снова нужен root-владелец; сложнее B без выигрыша.
- **D. Кнопка в панели.** Агент с доступом к HTTP-API нажмёт её сам. Для L3 запрещено, для L2 только как явный режим с аудитом (уже есть).

## Решение
1. Есть графическая сессия пользователя и `zenity`/`kdialog` → **канал A** (предупреждение об X11 в документах).
2. Иначе (или по выбору пользователя) → **канал B**: команда `service-admin approve <план>` показывает текст плана (как диалог) и вызывает `pkexec /usr/local/libexec/service-admin-approve` — root-скрипт читает запрос плана из каталога пользователя, показывает сводку, спрашивает `y/N` на **/dev/tty**, пишет решение в root-каталог (`plan_id`, `digest`, `decision`, срок). Панель исполняет план только если решение от root и `digest` совпадает.
3. Ни один канал недоступен или у пользователя passwordless-sudo → планы агентов L2/L3 не исполняются (`plan.no_approval_channel`).
4. L3 — только каналы A или B; режим «кнопка в панели» для L3 остаётся запрещён.

## Последствия
- Нужен установочный шаг с правами администратора (polkit-действие + скрипт-помощник); без него остаётся канал A.
- Тесты: подмена `zenity`/`pkexec` (как с `osascript`); проверка «агент того же пользователя не смог одобрить сам».
- Остаточные риски записываются в `docs/unverified.md` по итогам ревью.

## Требования к реализации (по итогам ревью, обязательны для Л2)
1. **Кто проверяет решение.** Одобрение имеет смысл, только если код, который его проверяет и исполняет план, агент не может подменить. Поэтому в Л2: исполняющая часть (проверка root-владельца решения, сверка `digest`, запуск операции) работает как **отдельная служба под другим пользователем/root** либо установлена в каталог, недоступный для записи пользователю панели; пока это не сделано, канал B считается защитой от случайных и «наивных» действий агента, но **не** от агента, меняющего код панели или внедряющегося в её процесс (`ptrace`, `kernel.yama.ptrace_scope`). Это записывается в «Остаточные риски».
2. **Повтор решения (replay).** Решение привязано к одноразовому `nonce`, который панель кладёт в запрос и в `digest`; использованные `nonce` панель запоминает. Срок действия решения короткий (минуты).
3. **Root-скрипт и каталог пользователя.** Скрипт: открывает запрос один раз с `O_NOFOLLOW|O_NONBLOCK`, проверяет через `fstat` (обычный файл, владелец = `PKEXEC_UID`, размер ≤ 64 КБ), читает байты один раз и **показывает и хеширует один и тот же буфер**; `plan_id` проверяется по `^[A-Za-z0-9-]{1,64}$` (никаких путей из argv); решение пишется атомарно (`O_CREAT|O_EXCL` + rename) в каталог `root:root 0755`.
4. **Кэш привилегий.** Действие polkit — строго `auth_admin` (не `auth_admin_keep`); для запасного пути `sudo` — `Defaults:ALL timestamp_timeout=0` для этой команды. Канал B **отключается** (`plan.no_approval_channel`), если у пользователя passwordless-sudo, polkit-правило без пароля для группы `wheel`/`sudo`, либо он состоит в root-эквивалентных группах (`docker`, `lxd`, `libvirt`, `disk`) — установщик предупреждает, а `/api/platform` показывает `approval.unsafe`.
5. **Канал A.** `zenity`/`kdialog` запускаются по **абсолютному пути** из системных каталогов (не из `PATH` пользователя). Остаточные риски: X11 (синтез ввода), Wayland с `ydotool`/`uinput` (группа `input`).
6. **Остаточные риски записываются** в `docs/unverified.md` и в руководство по подключению агента для Linux.

## Дополнения после ревью безопасности Л2 (реализовано)
- **Код подтверждения.** Помощник просит ввести случайный код, показанный только на экране человека; очередь ввода перед запросом сбрасывается (`tcflush`). Написать в tty человека или протолкнуть `y` через TIOCSTI можно, но кода агент не знает. Проверено в ВМ: «y» без кода → отказ.
- **Источник установки.** `install-approver.sh` отказывается ставить помощника, если любой компонент пути к нему доступен на запись пользователю панели.
- **Канал A против B.** Если диалог spoofable (X11 или группа `input`), а безопасный корневой помощник готов — выбирается помощник.
- **Небезопасные условия** расширены: `sudo` по абсолютному пути с чистым окружением (кэш 60 с), группы `incus`/`incus-admin`, правила polkit с `YES` без пароля.
- Помощник отказывает, если заданы и `PKEXEC_UID`, и `SUDO_UID`; показывает тип запроса (план агента / прямой вызов панели) и id; `direct-*` запросы CLI не выбирает автоматически; из текста убираются bidi/невидимые символы.
- **Остаточные риски (добавлено):** агент может писать в tty человека (скрытие/подмена экрана), поэтому в ADR защитой служит код, а не текст; CLI `service-admin` и оболочка принадлежат пользователю — безопаснее вызывать `pkexec /usr/local/libexec/service-admin-approve <id>` напрямую из доверенного терминала; NOPASSWD, ограниченный опасными программами, эквивалентен root и не обнаруживается.

## Дополнение (итоговое ревью, Л8)
- Панель **никогда не вводит** команду администратора в свой PTY (`sudo` показывается/копируется для собственного терминала владельца): агент того же пользователя мог бы подсмотреть или подставить ввод. Команда — `/usr/bin/sudo -k -- …`, GUI — `/usr/bin/pkexec` по абсолютному пути; повышение прав ищется только в системных каталогах.
- Помощник отказывается работать, если среди его предков — `server.py` (запуск из вкладки «Терминал» панели).
- API панели на Linux проверяет владельца клиентского сокета (`/proc/net/tcp`): другой локальный пользователь получает 403 (`srv.peer_forbidden`). На macOS не применяется.
- `~/.service-admin` — режим 0700; подсказка MCP-клиенту зависит от уровня агента.
