# ADR-0002: Гипервизор для ВМ и CI-раннеров на Linux

Статус: **принято (проект), реализация — этап Л4**.

## Контекст
На macOS ВМ делает `tart` (Apple Virtualization), изоляция сети — `softnet`. Панель управляет ВМ через интерфейс `Driver` и запускает одноразовые раннеры в клонах ВМ-основы. На Linux нужен драйвер с теми же свойствами: быстрый одноразовый клон, SSH внутрь, изоляция сети гостя, **без root** и без членства в root-эквивалентных группах — иначе отключается канал подтверждения агентов (ADR-0001).

## Варианты
- **Incus/LXD** (ВМ и контейнеры, образы, снимки): удобно, но управление — через сокет демона, доступный группе `incus-admin`/`lxd` = **root-эквивалент**. Отпадает для обычного пользователя панели.
- **libvirt (qemu:///system)**: нужен root или группа `libvirt` (root-эквивалент). `qemu:///session` без root есть, но сеть и снимки ограничены, зависимость тяжёлая.
- **QEMU напрямую** (`qemu-system-*` + `qemu-img`): без демона и без root; группа `kvm` (доступ к `/dev/kvm`) не root-эквивалент; клонирование — qcow2 с базовым образом (backing file) за доли секунды; SSH — проброс `hostfwd` на `127.0.0.1`; изоляция сети — пользовательская сеть QEMU: `restrict=on` + `guestfwd=…-cmd:` (реле `vm_relay.py` на каждое соединение гостя) на единственный адрес сервера CI. (Вариант `guestfwd` через chardev отброшен: он держит ОДНО TCP-соединение, открытое при старте ВМ, и сервер закрывает его по таймауту простоя — проверено на Gitea.)

## Решение
**QEMU напрямую.** Хранилище `~/.service-admin/vms/<имя>/` (`disk.qcow2`, `meta.json` 0600 с портом и паролем гостя, `qemu.pid`, `qmp.sock`, `qemu.log`); образы — `~/.service-admin/vm-images/`.
- **Клон** — qcow2 поверх неизменяемой основы; пока у основы есть клоны, её нельзя запускать и удалять (иначе испортятся наложенные диски). **Снимок/восстановление** — полная копия (`cp --reflink=auto`), без зависимостей.
- **База** создаётся из официального облачного образа Ubuntu (проверка sha256), первая загрузка настраивается cloud-init по `ds=nocloud-net` — адрес выдаёт крошечный HTTP-сервер панели на 127.0.0.1 на время первой загрузки.
- **Изоляция** (аналог softnet, строже): режим по умолчанию `server-only` — гость вообще без интернета и локальной сети, достижим только сервер CI (`guestfwd` на 10.0.2.100:порт, в госте имя сервера прописывается в `/etc/hosts`). Режим `none` (обычная пользовательская сеть) даёт гостю интернет **и** доступ к сети хоста — включается явно, с предупреждением. Интернет без доступа к локальной сети без root не получить — это записано как ограничение.
- **Ускорение**: `kvm`, если `/dev/kvm` доступен, иначе `tcg` (очень медленно; годится для проверки, не для работы).
- Пароль гостя — случайный на ВМ, SSH только на loopback.

## Последствия
- Нужны пакеты `qemu-system-<arch>`, `qemu-utils`, для aarch64 — `qemu-efi-aarch64`; ставятся из панели (apt, окно администратора/терминал).
- Проверка на Apple Silicon внутри tart-ВМ возможна только в режиме `tcg` (вложенной виртуализации нет); работу с `kvm` нужно подтвердить в CI на GitHub (runner с KVM) или на машине владельца.
- Контейнерный режим (Incus/Docker) для CI не делаем: код workflow должен исполняться в ВМ.

## Дополнения после ревью безопасности Л4 (реализовано и проверено в ВМ)
- **`restrict=on` всегда.** Без него гость видит loopback хоста (`10.0.2.2` → `127.0.0.1`) и мог бы ходить в API панели. Выход в интернет — только по явному `extra["internet"]` и только для доверенного рецепта `build` (пакеты apt; в этом режиме гость видит loopback хоста — рецепт ставит только пакеты Ubuntu). Раннеры на Linux всегда изолированы (`isolate=false` отклоняется: `runner.isolate_required`). Сборка основы тоже без сети: cloud-init берёт данные через `guestfwd` (10.0.2.100) к одноразовому HTTP-серверу панели с случайным токеном в пути.
- **Вход по ключу, пароля нет.** Для каждой основы создаются ключ клиента и ключ хоста гостя (ed25519); в cloud-init попадают только открытый ключ клиента и ключ хоста гостя. `ssh_pwauth: false`, пароль не создаётся (ни в `meta.json`, ни в cloud-init), ключ хоста гостя закреплён (`StrictHostKeyChecking=yes`, `known_hosts` ВМ, `HostKeyAlias`): пароль и токен регистрации не уйдут «подменному» sshd на 127.0.0.1 другого пользователя. Закрытый ключ хоста гостя после сборки удаляется на стороне хоста.
- **Образы по содержимому.** Облачный образ хранится как `<sha256[:16]>-<имя>.img` и никогда не заменяется на месте (на него ссылаются основы и клоны).
- **Блокировки** (`flock`) на время проверки и действия в `clone/copy/delete/rename/start`; журнал консоли гостя отключён (`-serial none`; только при сборке основы), запятые в путях QEMU удваиваются, `delete` не скрывает исходную ошибку раннера, перед сигналом процессу перепроверяется pid.
- **Остаточные риски:** контрольная сумма образа берётся с того же origin (подпись `SHA256SUMS.gpg` не проверяется); общий ключ клиента у основы и её клонов (гость хранит только открытую часть); в режиме `internet` (рецепт `build`) гость видит loopback хоста; на многопользовательском хосте порт SSH гостя (127.0.0.1:порт) доступен другим пользователям — вход возможен только по ключу.
